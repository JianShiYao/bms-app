# BMS 配置与标定模型 v0（设计契约）

> **定位**：本文细化 [architecture.md](architecture.md) 的 ADR-ARCH-007（配置、标定与硬件抽象边界）中**配置/标定治理**部分，是参数管理的**权威设计契约**——规定编译期配置、板级绑定、运行标定参数的**分层、元数据、校验/钳制、来源优先级、变更治理与消费方式**。**agent 据此实现或重构参数相关代码，代码向本契约对齐**；本文不描述现状实现。
>
> **现状与差距**不在此维护：见 [architecture.md](architecture.md) §11 迁移路径（本契约在"**引入可变安全参数前**"落地——当前保护阈值/诊断去抖时间等为桩，从桩变为可标定前须先满足本契约）。
>
> **规范措辞**：**必须 / 应 / 不得** 表示契约要求。相关：架构 [architecture.md](architecture.md) §10，数据契约 [data-model.md](data-model.md)（参数**不是** DB entry），诊断 [diagnostics-fault-model.md](diagnostics-fault-model.md)（去抖/老化时间是标定参数），安全 [safety.md](safety.md)（安全相关参数），接口 [../standard/module-interface.md](../standard/module-interface.md)。

## 1. 配置设计原则

- **参数不是运行数据**：可标定参数是**配置**，与 `bms_db` 的运行时快照（[data-model.md](data-model.md)）是两套机制。参数**不得**混入 DB entry；DB 存"当前测得/算得的值"，参数存"如何判断/计算的常量"。
- **一处声明**：每个可标定参数的名称、单位、类型、合法范围、默认值、版本、是否安全相关、owner、消费者，必须在**参数登记表**一处集中声明，供校验、标定、追溯与审计。
- **消费者不得硬编码**：protection/diag/soc/comm 等**不得**在逻辑里写死阈值/周期/容量；必须经统一参数访问获取。魔法数字**不得**散落在业务代码。
- **失效安全**：参数缺失、越界、版本不符、存储损坏时，**必须**回退到**安全默认值**并置 `bms_diag`；**不得**使用越界或来源不可信的参数进行 NORMAL 决策。
- **可追溯**：安全相关参数的默认值与变更必须可回指安全目标（[safety.md](safety.md) SG）与需求（追溯矩阵）。

## 2. 三层配置模型（契约）

| 层 | 载体 | 内容 | 何时确定 | 约束 |
|----|------|------|----------|------|
| **编译期配置** | Kconfig | 系统规模、启用/禁用模块、板级能力开关 | 构建时 | 影响裁剪与容量；不可运行时改 |
| **板级绑定** | devicetree + wrapper | AFE/CAN/GPIO/接触器反馈/预充等硬件资源与引脚 | 构建/板级 | 经 wrapper 暴露稳定接口（[architecture.md](architecture.md) §10、[hardware-abstraction.md](hardware-abstraction.md)） |
| **运行标定参数** | 参数登记表（默认值）+ 可选运行覆盖 | 保护阈值、滤波系数、容量、诊断去抖/老化时间、通信周期等 | 默认编译期定；可选 NVM/上位机覆盖 | 必须满足 §3–§7 全部契约 |

- Kconfig 可作为早期参数载体，但**不得**把"参数治理"简化为"加一个 Kconfig"——凡属**运行标定参数**（尤其安全相关），必须具备 §3 的完整元数据，而非仅一个裸 `CONFIG_*` 数值。
- 编译期与板级配置**不得**承载需要现场标定或版本化管理的安全阈值。

## 3. 参数元数据契约（登记表）

每个**运行标定参数**必须声明下列字段（参数登记表，foxBMS 配置思路，Zephyr 原生落地）：

| 字段 | 含义 | 约束 |
|------|------|------|
| `id` | 稳定枚举（如 `PARAM_CELL_OV_MV`） | 全局唯一、不复用、变更即配置变更 |
| `unit` | 物理单位（mV/mA/0.1℃/ms/mAh…） | 必须显式；消费者按声明单位使用，**不得**隐式换算 |
| `type/range` | 类型与合法范围 `[min,max]` | 安全相关参数必须有有限范围 |
| `default` | 安全默认值 | 必须是"即便无其他来源也安全"的值 |
| `version` | 参数集版本/schema 版本 | 用于校验与迁移 |
| `safety` | 是否安全相关 | 决定变更治理与钳制强度（§4） |
| `owner` | 负责定义/维护的模块 | 单一 owner |
| `consumers` | 读取该参数的模块 | 便于影响面分析 |

> 单位/范围/默认值本身也是需被评审的设计决策；数值不在本文冻结，本文只规定"每个参数必须带齐这些元数据且集中登记"。

## 4. 安全相关参数的额外约束（契约）

- **范围钳制**：安全相关参数在使用前**必须**钳制到声明范围；越界值**必须**被拒绝并回退安全默认 + 置 `bms_diag`（不得静默截断为端点后照常使用于 NORMAL 判定）。
- **变更治理**：安全相关参数（保护阈值、接触器/预充时序、诊断去抖时间等）的默认值或范围变更，**必须**走设计评审（[../process/design-review.md](../process/design-review.md)）并更新追溯矩阵；版本号必须递增。
- **保守方向**：当不确定时，安全参数默认值**应**取更保守（更早保护/更早失效安全）的一侧。
- **来源可信**：仅经校验通过的来源（§6）可提供安全参数；不可信/未校验来源**不得**用于安全决策。

## 5. 参数消费方式（契约）

- 消费者通过**统一参数访问**读取（如 `bms_param_get(id)` 或生成的强类型只读结构），**不得**直接引用其他模块内部变量或硬编码常量。
- 典型消费（对齐各设计契约）：
  - `bms_protection` ← 过压/欠压/过流/过温阈值、迟滞（[safety.md](safety.md)）。
  - `bms_diag` ← 各诊断条目的 `confirm_time_ms`/`clear_time_ms`/老化策略（[diagnostics-fault-model.md](diagnostics-fault-model.md) §2·§5）。
  - `bms_algorithm`(soc) ← 容量、库伦效率、滤波系数。
  - `bms_comm` ← 上报周期、超时。
  - `bms_bms`/`bms_contactor` ← 预充超时、电压爬升判据（[architecture.md](architecture.md) §7）。
- 参数读取是**只读**：消费者不得写回参数；参数变更只经标定路径（§7）。

## 6. 来源优先级与校验（契约）

- **来源优先级**（低→高，若启用）：编译期默认值 → NVM 持久化标定 → 上位机在线下发（受权限与安全约束）。高优先级来源仅在**校验通过**后生效。
- **加载即校验**：任何非默认来源的参数集在生效前**必须**校验：schema/版本匹配、逐参数范围、（如有）完整性/校验和。任一项失败 → **整集拒绝**、回退默认、置 `bms_diag`。
- **掉电/损坏 fail-safe**：NVM 缺失/损坏**不得**导致使用随机值；必须回退安全默认并诊断记录。
- 安全参数的在线下发在真机阶段须受权限校验（由 `bms_sys` 授权，见 [architecture.md](architecture.md) §7），本契约先规定"未授权/未校验不得生效"。

## 7. 标定流程与治理（契约）

- **谁能改**：编译期/板级参数经代码评审改；运行标定参数经标定路径改，安全相关的须评审 + 追溯 + 版本递增（§4）。
- **变更验证**：安全相关参数变更**必须**有对应验证（测试/分析），并在追溯矩阵登记其影响的需求与安全目标。
- **版本化**：参数集变更递增 `version`；消费侧以版本校验拒绝不兼容集。

## 8. 仿真与真板（契约）

- `native_sim`/QEMU 阶段：参数以**编译期默认值**为准，NVM/上位机来源可桩化或禁用；桩化**不得**放宽安全默认或跳过范围校验。
- 真板阶段：NVM/上位机来源按 §6 启用，硬件访问经 wrapper（[hardware-abstraction.md](hardware-abstraction.md)）。

## 9. 可测性约束

- 参数**校验与钳制**必须为纯函数（如 `param_validate(set) → ok/err`、`param_clamp(id,val)`），可脱离硬件/NVM 单测：合法集通过、越界/版本不符/损坏被拒并回退默认。
- 消费路径可注入参数：以注入的阈值/时间验证 protection/diag/soc 行为（对齐各契约的可测性约束）。

## 10. 迁移

本契约落地阶段见 [architecture.md](architecture.md) §11：在"**引入可变安全参数前**"落地——即当前作为桩的保护阈值、诊断去抖时间等**从硬编码/桩转为登记表管理的可标定参数**时，必须先满足本契约（元数据、校验钳制、fail-safe、消费方式）。迁移期允许桩与登记表共存，但**目标以本契约为准**；每步保持既有 CI 与 ztest 通过。
