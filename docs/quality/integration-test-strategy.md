# 测试策略

> **文档定位**：本文定义 bms-app 的测试分层与验证边界。它不是门禁事实表；门禁事实以 [gates.md](gates.md) 为准。本文回答的是：各层测试验证什么、放在哪、什么时候算够。

## 1. 目标

这套策略的目标不是“把测试做满”，而是把验证拆到合适的层：

- 单元测试先把纯逻辑、边界和不变量压稳。
- 接口测试确认模块对外契约、数据流和错误处理不走样。
- SITL 先把完整软件栈拼起来，验证调度、状态流和跨模块时序。
- 故障注入专门覆盖无效、过期、丢失、超时和异常恢复。
- HIL 把真实硬件行为补上，验证仿真看不到的 IO、时序和复位。
- 系统测试验证完整特性在真实使用路径上的端到端结果。

## 2. 分层定义

| 层级 | 主要位置 | 验证重点 | 典型断言 |
|---|---|---|---|
| 单元测试 | `tests/bms/<module>` | 纯函数、边界值、状态转移、不变量 | 返回值、状态变化、错误码、无副作用 |
| 接口测试 | `tests/integration/<topic>` 或模块级测试套件 | 模块间 API、DB entry、zbus 语义、调用契约 | 数据一致、owner 约束、错误传播 |
| SITL 测试 | `native_sim` / QEMU / host 可运行仿真 | 线程调度、任务编排、模块拼装、日志与配置组合 | 一轮流程可跑通，状态链正确 |
| 故障注入 | 集成/系统测试中的专项用例 | invalid / stale / timeout / 丢包 / 诊断触发 / 复位异常 | 失效安全态成立，恢复路径明确 |
| HIL 测试 | 真板 / 台架 / 自托管 runner | 真实 GPIO、AFE、接触器、看门狗、NVM、复位 | 物理 IO 和时序满足预期 |
| 系统测试 | `tests/integration/<feature>` / 端到端套件 | 用户可见场景、跨模块闭环、发布准出 | 功能完成，安全链不被破坏 |

## 3. 各层说明

### 3.1 单元测试

单元测试是第一道门，优先覆盖纯逻辑代码。

适合验证：

- 边界值、NULL、越界、非法状态。
- 纯函数的输入输出映射。
- 诊断、保护、SOC、参数合法化等可独立计算的逻辑。

要求：

- 尽量不依赖真实时间、线程和硬件。
- 测试名能看出验证的需求或契约。
- 每个关键用例顶部写 `/* Verifies REQ-... */`。

### 3.2 接口测试

接口测试验证“模块之间怎么说话”，不是只验证单个函数。

适合验证：

- `bms_db` 读写契约。
- `bms_diag` 聚合规则。
- `bms_bms` 状态机与保护/诊断的联动。
- `zbus` 发布/订阅语义和数据传播。

要求：

- 重点断言接口契约、字段一致性、owner 边界。
- 可以用 fake/stub 层替代硬件，但不要替代整个模块链。
- 不要把纯函数测试塞进接口测试里。

### 3.3 SITL 测试

SITL（Software-in-the-Loop）是完整软件栈在仿真环境里的组合验证。

适合验证：

- task pipeline 是否按预期推进。
- 模块组合后，状态、日志、诊断、上报是否一致。
- 配置变化是否改变组合行为。

推荐落点：

- `native_sim` 作为主路径。
- QEMU 可作为补充预检，但不要拿它替代 Linux/native_sim 权威结果。

### 3.4 故障注入

故障注入不是单独一层“可有可无”的测试，而是每层都要刻意覆盖的策略。

应覆盖的故障类型：

- 无效输入：`NULL`、越界、非法枚举、错误范围。
- 过期数据：stale snapshot、超时、失联。
- 诊断故障：ERROR / CRITICAL / latch / clear 触发。
- 传感器异常：丢样、抖动、值突变、短路/开路抽象。
- 存储异常：默认值回退、NVM 损坏、读写失败。

准则：

- 故障注入优先服务安全链。
- 失效安全态必须有明确断言，例如接触器保持 OPEN。
- 故障恢复路径和故障保持路径都要测。

### 3.5 HIL 测试

HIL 是把真实硬件行为补进来的一层，不是仿真替代品。

适合验证：

- AFE、GPIO、接触器、继电器、ADC、IWDG、NVM 的真实行为。
- 复位、上电、掉电、时序和延迟。
- 保护动作是否真的能驱动执行器进入安全态。

要求：

- HIL 只验证仿真看不到的物理行为。
- 关键安全路径最终要落到 HIL 证据。
- HIL 结果要能回链到需求和测试用例。

### 3.6 系统测试

系统测试验证的是“一个特性是否真的完成了”，通常是端到端视角。

适合验证：

- 新特性的完整用户路径。
- 多模块协作下的行为一致性。
- 发布前的回归与准出。

要求：

- 系统测试不替代单元测试和接口测试。
- 系统测试要覆盖正常路径和至少一条失效路径。
- 若涉及安全链，系统测试必须说明 HIL 或故障注入的补充证据。

## 4. 推荐顺序

| 顺序 | 层级 | 说明 |
|---|---|---|
| 1 | 单元测试 | 先把纯逻辑锁住 |
| 2 | 接口测试 | 再把模块边界锁住 |
| 3 | SITL 测试 | 然后拼起完整软件栈 |
| 4 | 故障注入 | 在关键链路上补异常场景 |
| 5 | HIL 测试 | 最后把真实硬件行为补齐 |
| 6 | 系统测试 | 形成端到端准出证据 |

## 5. 目录建议

```
tests/
  bms/
    <module>/           # 单元测试
  integration/
    <topic>/            # 接口测试、SITL、系统测试、故障注入
  hil/
    <board-or-feature>/ # 真板/HIL 场景（如果已建立）
```

## 6. 与 CI 的关系

- 单元测试和接口测试优先进入 `twister`。
- SITL 测试优先在 `native_sim` 上跑，QEMU 仅做补充。
- 故障注入测试优先和接口测试、系统测试绑定，不单独漂浮。
- HIL 当前不属于默认 CI 必过门，但应进入阶段性里程碑和发布准出证据。
- 系统测试在特性级 PR 中至少提供一条端到端证据，尤其是安全链改动。

## 7. 准出标准

一次涉及 engine、safety、diagnostics、task pipeline 或 comm 的 PR，至少满足：

- 相关单元测试通过。
- 相关接口测试或 SITL 测试通过。
- 安全相关改动至少有一条故障注入或失效安全测试。
- 涉及硬件行为的变更有 HIL 计划或 HIL 结果。
- traceability 中能看到每条关键需求的验证方法。

## 8. 优先补齐项

当前优先补的方向：

- `bms_task + bms_db + bms_diag + bms_bms` 的接口测试。
- safety 链路的故障注入用例。
- 真板上线后，把 HIL 证据补到关键保护路径。
- 将已有系统级样例拆成可复用的 `integration/` 套件。
