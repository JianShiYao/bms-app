# 敏捷+V 研发方法论(母文档)— 设计文档

- 日期：2026-06-24
- 项目：EnerVenue BMS 固件（Zephyr 4.4.0 + CMake）
- 交付物：新增 `docs/development-methodology.md`（通用敏捷+V 方法论母文档）+ 配套回改
- 产出语言：中文

## 1. 目的与背景（为什么做）

项目已有完整的**操作层**文档,但缺一份**指导性的方法论母文档**:
- `superpowers/specs/2026-06-19-bms-agile-v-agents-design.md` 是 **agent 体系设计**,不是方法论;
- `agents-guide.md` 是 **agent 用法**;
- `development-workflow.md` 是 **门禁与集成**(上一轮新增的 §1 仅为小 V 骨架 + 交叉链接);
- `templates/` 是 **ID 与追溯模板**。

后果:敏捷+V 的"为什么这么设计""不可违背的原则"散落或缺失,下游各文档**没有共同的依据来源**,
团队/agent 对方法论的理解无统一出处。development-workflow §1 的"设计依据"目前链向 agent 设计 spec——名不符实。

**意图**:新建 `docs/development-methodology.md` 作为**通用敏捷+V 研发方法论母文档**——它是开发工作流、
agent 体系、模板等一切下游的**依据(rationale / source of authority)**,所有下游流程**由它衍生**。
核心价值有二:**统一团队(与 agent)对方法论的认知**;**为下游提供可引用的唯一依据**。

## 2. 已锁定的设计决策（brainstorming 结论）

1. **层次 = 方法论概念层**(非操作 SOP、非 agent 设计)。它是母文档,下游皆为其落地/派生。
2. **体量 = 中间档(C)**:以"指导宪章"为主干,关键处(尤其"敏捷+V 为何能调和""可追溯性为何是灵魂")
   补足"为什么",但不展开成长篇教材。
3. **风格 = 通用方法论为主干 + BMS 注脚**:方法论可独立站立、可复用;BMS 具体(zbus/失效安全/Zephyr/native_sim)
   仅以**旁注/注脚**形式出现在"原则落到本项目"处。
4. **与 development-workflow §1 的分工 = A**:方法论内容**上移**到本母文档;§1 **瘦身**为"指针 + BMS 落地规则"
   (分支/PR 粒度、ztest 注释格式等本项目具体规则保留在 §1)。
5. **组织框架 = 混合(框架3)**:短"为什么" → 核心模型(主干) → 不可违背原则 → 派生关系图。
6. **核心定位 = 依据**:第 6 节"派生关系"是支点——明确每个下游文档"依据本方法论的哪一部分"。

## 3. 母文档结构（`docs/development-methodology.md`）

通用方法论 + BMS 注脚;中间档深度。七节:

### §1 目的与适用范围
- 本文是什么、给谁看(开发者 + agent 体系 + 新人,用于统一认知);
- 一句话宣示:**所有下游研发流程(开发工作流、agent、模板、CI 门禁)均以本方法论为依据并由其衍生**;
- 派生关系总览(详见 §6)。

### §2 为什么是敏捷+V（认知统一核心 · key why）
- 通用陈述:纯敏捷 / 纯 V 各自的局限,尤其对"**安全相关 + 长周期 + 资源/实时约束**"的系统;
- **调和洞察**:敏捷管节奏、V 管完备性与可追溯,**自动化是让两者共存的桥**(把人工的"严"变成持续的"严");
- BMS 注脚:本项目属安全相关系统(保护/接触器),故 V 的"可追溯+完备验证"不可省;但单人/迭代式开发需要敏捷的快。

### §3 核心模型:敏捷外壳 + 小 V 内核（主干）
- **迭代层(敏捷)**:backlog 驱动,每迭代交付一个特性增量;
- **每特性走"小 V"**:左腿(需求→架构→详细设计)逐层对应右腿(系统/集成验证 ↔ 需求、单元测试 ↔ 详细设计);
- 小 V 示意图(复用既有约定);
- 轻点**双轨**(探索性工作 vs 交付性工作)作为可选实践,不强制。
- BMS 注脚:特性即模块增量(如"补全 SOC 库仑计数");集成/系统验证当前合并(单一 native_sim 目标,YAGNI)。

### §4 五条指导原则（不可违背）
每条 = 通用陈述 + BMS 注脚:
1. **软件优先 / 可仿真**:逻辑与硬件解耦,大部分开发/测试不依赖硬件。〔BMS:zbus 解耦五模块;native_sim/QEMU 先行,真板后随〕
2. **测试左移 / 测试金字塔**:能在低层(单元/PC)测的绝不上推;上硬件只测真正硬件相关项。〔BMS:纯逻辑函数 + 薄线程包装,ztest 直测纯函数〕
3. **可追溯性是灵魂**:每条需求贯通 `需求→设计→代码→测试`,右腿可回溯左腿;无追溯即无完备性证据。〔BMS:`REQ-<域>-NNN→DES-<域>-NNN→code→ztest`,ztest 注释 `/* Verifies REQ-... */`〕
4. **失效安全 / 安全红线先行**:安全相关需求优先、默认安全态、测试先行。〔BMS:接触器默认 OPEN,仅 NORMAL 才 CLOSED;保护线程最高优先级〕
5. **持续合规(自动化为桥)**:验证与追溯靠自动化持续满足,而非阶段末人工补;门要前移、高频、自动。〔BMS:CI 6 门 + pre-commit/pre-push 分层门禁〕

### §5 迭代生命周期与门
- 通用 **DoR/DoD** 原则(准入:依赖就绪/基线可测/范围界定;准出:产出齐备/追溯无断链/安全项有测试/门全绿/范围受控);
- 小 V 各阶段与"门即持续合规"的关系;
- **具体门禁与命令向下指向** `development-workflow.md`(不在母文档复制)。

### §6 派生关系:本方法论如何落地（支点）

## 5. 范围与非目标（YAGNI）

- **不做**:展开成嵌入式工程教科书(约束/调和只讲到够指导决策即止);复制 development-workflow 的命令/门禁细节;
  重写 agent 设计 spec;引入 ISO 26262 工作产物全集。
- **保留**:通用方法论可独立复用(BMS 仅注脚),便于将来其他固件项目借用。

文档类交付,验证以"自洽 + 依据关系成立 + 无重复"为准:
1. 母文档能独立回答"为什么敏捷+V / 小 V 是什么 / 不可违背的原则 / 谁从它衍生";
