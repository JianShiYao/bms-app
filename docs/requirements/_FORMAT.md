# S16100B 需求规格 · 共享格式规范

> 本目录下的需求是对 `S16100B_Demo` 现有固件**逆向提炼**的结果（描述"代码当前做了什么"，
> 并以需求语言重述）。与 bms-app 的需求工程规范对齐：`REQ-<域>-NNN` + EARS 句式 + 可度量验收准则。

## ID 规范

- 需求 ID：`REQ-<域>-NNN`（三位序号，从 001 起）。
- 域代码：`CTRL`(状态机/接触器) `PWR`(电源/时间/看门狗) `AFE`(采集/均衡) `SOC`(电量/容量)
  `PROT`(保护/告警) `COMM`(通信) `PARA`(参数/存储) `LOG`(日志) `OTA`(升级) `HEAT`(加热)
  `LED`(指示) `CHG`(充电管理)。

## 单位基线（与代码一致）

| 量 | 单位 | 约定 |
|---|---|---|
| 电压 | mV | — |
| 电流 | mA | 充电为正 / 放电为负（以代码实际符号为准，存疑则注明） |
| 温度 | 0.1℃（部分接口 1℃，按代码注明） | — |
| 容量/电量 | mAh | — |
| SOC/SOH/SOP | 1%（部分内部为 0.1%/‰，按代码注明） | — |
| 时间 | ms / s（按代码字段后缀注明，如 `_ms`） | — |

## 每条需求的写法

### REQ-<域>-NNN  <简短标题>

| 属性 | 内容 |
|---|---|
| 类型 | 功能 / 安全 / 性能 / 接口 / 约束 |
| 安全相关 | 是 ⚠️ / 否 |
| 来源（源码） | `文件:函数()`（如 `BMS_Control.c:BmsControlTask()`），有行号更好 |
| 验证方法 | 测试 / 分析 / 检视 / 演示 |
| 状态 | 已实现（来自代码）/ 存疑 / 缺口 |

**需求描述（EARS 句式）**
> 当 <触发/条件> 时，系统应 <可观察的响应>。（普遍型"系统应始终…"；状态型"在<状态>期间…"；不期望型"如果…则…"）

**理由 / 代码依据**
> 为什么有这条需求 + 代码里如何体现（关键变量、阈值、分支）。

**验收准则（可度量）**
- Given … When … Then …（阈值/时限/单位写清）。

## 提炼原则

1. **忠于代码**：描述代码"实际"行为，不臆造"应该有但代码没有"的需求。代码缺失但显然应有的，标 `状态=缺口` 并说明。
2. **数值带单位**：所有阈值/默认值标单位，并注明来源（宏/默认参数/硬编码）。
3. **安全优先标注**：凡涉及接触器开合、过压/过流/过温/短路保护、失效安全的，`安全相关=是 ⚠️`。
4. **存疑单列**：注释与代码矛盾、magic number 含义不明、疑似 bug 的，`状态=存疑` 并在文末"存疑与观察"小节展开。
5. **可追溯**：每条需求 `来源（源码）` 必填，便于回查。
