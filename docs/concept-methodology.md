# 安全案例驱动的敏捷+V 研发方法论

本文是本项目研发方法论的**根基(母文档)**:一份**安全案例驱动的敏捷+V 研发方法论**,BMS 项目相关的具体落地以「BMS 注脚」形式给出。

> **定位**:开发工作流、agent 体系、需求/追溯模板、CI 门禁等一切下游流程,**均以本方法论为依据并由其衍生**(派生关系见 §7)。
> **读者**:开发者、参与研发的 agent、新人——用于**统一对方法论的认知**。
> **边界**:本文只讲"为什么 / 是什么";**具体操作**(门禁命令、分支/PR、agent 调用)见各下游文档,本文不复制。
>
> **升级方向**:本方法论不是用敏捷替代 V,也不是回到重型大 V;它是在"敏捷外壳 + 小 V 内核"之上补上**风险分级、证据包、安全案例与分层实物验证**。对 BMS 固件而言,更优路线是 **Agile + V + Safety Case + CI/HIL Evidence**。

---

## 1. 目的与适用范围

- **是什么**:把"为什么用敏捷+V、小 V 是什么、哪些原则不可违背"集中成唯一出处,作为下游流程的共同依据。
- **解决什么**:避免方法论散落各文档导致理解不一、维护脱节;让下游有可引用的单一依据。
- **怎么用**:做任何研发决策(定流程、设门禁、写 agent、建模板)时,应能回指本文的某条模型或原则;若回指不到,要么决策有问题,要么本文需补充。

派生关系总览见 §7。

## 2. 为什么是敏捷+V+安全案例(统一认知的核心)

软件工程的成熟实践(敏捷、CI/CD)多诞生于互联网领域,其隐含前提——运行环境随处可得、部署近零成本、错误可快速回滚——在**安全相关 + 长周期 + 资源/实时约束**的嵌入式系统里大多不成立。于是两种纯粹方法各有死角:

- **纯敏捷的死角**:轻文档、轻追溯、拥抱变化。快,但**无法举证"每条(安全)需求都被设计覆盖、被测试验证"**——撞上功能安全的墙。
- **纯 V 模型的死角**:需求前置、逐级验证、文档与追溯完备。严谨可举证,但大批量、阶段门、**人工**验证与追溯使其**慢、不适应迭代**。

**调和洞察(本方法论的支点)**:敏捷与 V 并非二选一,而是分层共存——
> **敏捷管节奏,V 管完备性与可追溯;而 V 模型的"慢"主要慢在人工(人工写验证、人工维护追溯)。一旦把验证与追溯自动化,V 的完备性就能以敏捷的节奏被持续满足——自动化是让两者共存的桥。**

这条洞察贯穿后面的模型(§3)、原则(§4 尤其原则5)与门(§5)。

**张力的第二个轴——变更**:上面调和的是"节奏 vs 完备性"。但敏捷与 V 最尖锐的冲突在**变更**——敏捷拥抱变化,而 V 的完备性证据(追溯链)在需求改动时最易断裂。调和同样靠"桥":**变更必须连带传播——把追溯链与受影响的右腿验证一起再基线,否则完备性证据当场失效**(见 §4 原则6 与 §5)。

> **BMS 注脚**:本项目是安全相关系统(过压/过流/过温→接触器),V 的"可追溯 + 完备验证"不可省;同时以迭代方式快速演进骨架,需要敏捷的快。两者靠 CI 与分层门禁的自动化共存。
>
> **增强判断**:对研究/原型阶段,敏捷+小 V 足够支撑快速演进;对接真板、客户审核、量产或功能安全目标明确后的阶段,仅有追溯链还不够,必须把危险分析、风险等级、验证强度、测试证据、评审记录与发布基线组织成可审计的**安全案例**。

## 3. 核心模型:敏捷外壳 + 小 V 内核 + 安全案例证据层

**迭代层(敏捷外壳)**:以 backlog 驱动,每个迭代交付一个**特性增量**。

**证据层(安全案例)**:以风险与安全目标为索引,持续收集需求、设计、代码、测试、评审、分析与发布基线证据;证据不是阶段末补材料,而是随小 V 同步生成。

**每个特性走一个「小 V」**(左腿分解·设计,逐层对应右腿验证·集成):

```
左腿（分解·设计）                                右腿（验证·集成）
① 需求 ─────────────────────────验证──────▶ ⑤ 测试·系统/集成级
② 架构 ────────────────────验证──────────▶ （集成验证并入系统/集成级）
③ 详细设计 ──────────验证──────────────────▶ ⑤ 测试·单元级
            └──────────▶ ④ 编码实现 ──────────────┘
   贯穿：⑥ CICD 持续验证 · 可追溯链(需求→架构→设计→代码→测试) · 代码评审 · 安全案例证据包
```

- **左右腿逐层对应**:右腿每一层验证回溯到左腿同层的需求/设计——这是"完备性可举证"的结构来源。
- **编码在谷底**:设计向下收敛到实现,再由测试向上逐层验证。
- **双轨(可选实践)**:高不确定的工作(架构选型、算法探索、危险分析)走**探索轨**,想清楚后再喂给**交付轨**走严格小 V;不要硬塞进固定迭代假装有进度。
- **风险分级验证**:普通功能按测试金字塔推进;安全相关功能按风险等级提高验证强度,必要时增加故障注入、HIL/台架验证、边界/降级场景和独立评审。

> **BMS 注脚**:一个"特性"通常是一个模块增量(如"补全 SOC 库仑计数""接触器 GPIO 驱动")。当前执行型验证仍以 `native_sim`/QEMU 为主,`qmxx_f407zg` 已作为真机 bring-up 构建目标纳入 CI;因模块化且暂无执行型多目标差异,**集成测试与系统测试暂合并**为一个验证环节(YAGNI);将来真机执行型目标增多再拆。

## 4. 七条指导原则(不可违背)

每条先给通用陈述,再附 BMS 注脚。下游的任何流程/门禁/agent 职责,都应能回指其中一条或多条。

1. **软件优先 / 可仿真** — 软件独立于硬件演进;仿真目标是一等公民,使大部分开发与测试脱离硬件。
   > BMS:`native_sim`/QEMU(`mps2/an386`)为主力验证目标,`qmxx_f407zg` 为 bring-up 构建目标,`bms_f405` 为目标板;架构以 **engine core**(`bms_task`/`bms_db`/`bms_diag`/`bms_bms`)集中调度、数据交换与诊断,zbus 作为过渡/边界通信机制,逻辑不绑死硬件。

2. **测试左移 / 测试金字塔** — 逻辑与硬件解耦;能在低层(单元/PC)拦截的缺陷绝不上推;上硬件只验证真正硬件相关项。
   > BMS:核心逻辑放纯函数(`bms_protection_evaluate`、`bms_soc_coulomb_step` 等)+ 薄线程包装,Twister ztest 直测纯函数。

3. **可追溯性是灵魂(V 模型核心)** — 每条需求贯通 `需求→架构→设计→代码→测试`,右腿验证可回溯左腿;**无追溯即无完备性证据**;安全相关需求优先自动化测试。
   > BMS:`REQ-<域>-NNN → DES-<域>-NNN → 代码位置 → ztest 用例`;域 = SYS/AFE/SOC/PROT/BAL/COMM/BOARD;ztest 用 `/* Verifies REQ-<域>-NNN: ... */` 回链。
   >
   > **立场(原则即刻生效,不悬空)**:本原则对**新特性即刻强制**——小 V 的 DoD 要求追溯链无断链,无追溯不得合并。历史代码(逆向得到的既有需求)的追溯矩阵作为**独立的增量 backfill** 推进,不因历史欠账而削弱对新工作的强制。

4. **失效安全 / 安全红线先行** — 安全相关改动必须关联安全需求、默认安全态、测试先行、显式验证。
   > BMS:接触器**默认 OPEN**,仅判定 NORMAL 才 CLOSED;保护线程最高优先级;SOC 等信息流不得参与保护决策。
   >
   > **立场(纪律不分阶段)**:安全**纪律**——关联安全需求、测试先行、验证失效安全默认态(见 [process-workflow.md §2](process-workflow.md))——**现行生效,不分项目阶段**。仅 FMEA / 危害分析 / ISO 26262 工作产物全集等**重型**项可随"接真板、明确安全目标"后置。

5. **持续合规(自动化是桥)** — 验证、追溯与证据靠自动化**持续**满足,而非阶段末人工补;门要前移、高频、自动。这是 §2 调和洞察的落地。
   > BMS:pre-commit/pre-push/`check.ps1`/CI 分层门禁 + DoD 追溯门;**当前 CI 阻断门与阈值以 [quality-gates.md](quality-gates.md) 为准**(本文不复制);后续接入真板/HIL 后,硬件相关验证结果也应进入同一证据链。

6. **变更即再基线(变更不破坏追溯)** — 需求或安全相关项在迭代中途 / 跨迭代变更时,必须**连带更新**其追溯链(需求→架构→设计→代码→测试)与**受影响的右腿验证**;未同步即视为**断链**。这是原则3在"变化"维度的延伸,也是 §2 调和洞察的第二个轴——变更的完备性靠"连带传播"维持。
   > BMS:改 `REQ-PROT-*` 阈值 → 同步对应 `DES-*`、代码与 ztest 并更新 `traceability.md`,重跑受影响用例;失效安全项变更按 [process-workflow.md §2](process-workflow.md)。

7. **风险分级 / 安全案例驱动** — 危险分析决定验证强度,安全目标决定证据组织方式;每个安全相关目标都应能回指一组可审计证据(需求、设计、代码、测试、评审、分析、发布基线)。没有风险分级,测试容易平均用力;没有证据包,追溯链难以支撑审核。
   > BMS:过压/过流/过温、采样异常、接触器粘连、预充失败、通信丢失等场景应进入危险分析;高风险项至少要求边界测试、故障注入、默认安全态验证,接真板后逐步补 HIL/台架证据。

## 5. 迭代生命周期与门

- **为什么要 DoR/DoD**:迭代是流动的,需要明确"什么时候可以进、什么时候算完",否则容易把没想清楚的工作塞进迭代、或在追溯/验证不全时就宣称完成。
  - **准入(DoR)原则**:依赖就绪、基线可构建可测、范围(含非目标)已界定。
  - **准出(DoD)原则**:小 V 各阶段产出齐备;**追溯链无断链**;**变更已再基线**(改动的需求/安全项,其追溯链与受影响右腿同步更新);安全相关项有对应测试并通过;风险分级与证据包已更新;自动化门全绿;范围受控。
- **门即持续合规**:把 V 的"阶段门"从"开会才过"变成"每次提交都过"——前移、高频、自动(原则5)。
- **具体门禁、命令、DoR/DoD 的本项目落地清单**见 [process-workflow.md](process-workflow.md),本文不复制。

## 6. BMS 功能安全增强层(从原型到量产的补足)

本节定义在现有敏捷小 V 之上逐步补强的能力。它们不要求在原型第一天全部重型化,但一旦进入真板验证、客户交付、量产准备或功能安全目标明确阶段,就应成为 DoR/DoD 与发布基线的一部分。

> **范围提示**:本节中的 HIL/FMEA/HARA/FTA/MCUboot 等**不是当前每个 PR 的默认硬门**,除非改动触发安全/硬件/发布基线要求。当前现行强制项以 §4 原则与 [quality-gates.md](quality-gates.md) 为准。

### 6.1 风险分析与安全需求

- **输入**:系统边界、运行模式、能量路径、电芯/模组/Pack 约束、接触器/预充/采样/通信失效模式。
- **方法**:按项目阶段选择 HARA、FMEA、FTA、STPA 或轻量等价表;早期可轻量,但必须能追溯到安全需求。
- **输出链**:`Hazard/失效模式 → 安全目标 → 功能安全需求(FSR) → 技术安全需求(TSR) → REQ/DES/代码/测试`。
- **BMS 重点场景**:过压、欠压、过流、短路、过温、采样卡死/漂移/越界、AFE 通信异常、接触器粘连、预充失败、绝缘/高压互锁相关输入异常、CAN 通信丢失、NVM 参数损坏。

### 6.2 需求与追溯元数据

每条安全相关需求除 `REQ-<域>-NNN` 外,建议至少补充:

| 字段 | 用途 |
|---|---|
| 来源 | 标明来自危险分析、客户需求、法规/标准、架构约束或缺陷修复 |
| 风险等级 | 决定验证强度与评审要求 |
| 验收准则 | 明确可观察的通过条件 |
| 验证方式 | unit / integration / native_sim / QEMU / SIL / PIL / HIL / bench |
| 失效安全策略 | 默认态、降级态、恢复条件 |
| 变更历史 | 支撑再基线与审核 |

### 6.3 验证阶梯与触发条件

验证从便宜、快速、可重复的层级开始,逐步走向真实硬件:

`unit → component → native_sim → QEMU → SIL → PIL → HIL → bench/pack`

- **unit/component**:纯函数、状态机、边界条件、参数检查、故障输入。
- **native_sim/QEMU**:线程、zbus、模块集成、配置组合、基础时序。
- **SIL/PIL**:算法、编译器/目标差异、定点/浮点/溢出行为。
- **HIL/bench**:采样链路、AFE、接触器、预充、真实 IO、故障注入、保护响应时间。

触发拆分条件:出现真机目标、硬件相关缺陷、保护响应时间要求、客户/审核证据要求、或 native_sim/QEMU 无法覆盖的外设交互时,不得继续把集成/系统/硬件验证混为一个环节。

### 6.4 实时性、资源与鲁棒性门

BMS 固件不仅要"算对",还要"及时、安全、资源可控"。建议**视阶段**把以下指标纳入质量门或发布检查:

- 保护响应时间、任务周期、调度优先级、watchdog 喂狗路径。
- 栈使用、RAM/Flash、CPU load、队列深度、消息丢失/阻塞策略。
- ISR 延迟、采样周期抖动、通信超时、NVM 读写失败与恢复。
- 编译器告警、静态分析、MISRA/CERT C 子集、复杂度、未定义行为风险。

### 6.5 接口、参数与标定治理

- **接口契约**:对 AFE、GPIO、CAN、NVM、接触器、预充、电流/电压/温度采样定义单位、范围、周期、默认值、错误码、超时与降级行为。
- **参数治理**:保护阈值、滤波参数、SOC 参数、温度限值等必须有版本、单位、合法范围、默认值、变更审批与测试覆盖。
- **变更影响分析**:参数或接口变更必须回答影响哪些安全目标、需求、模块、测试、标定文件、发布说明与现场兼容性。

### 6.6 发布基线与证据包

一次可交付发布至少应能冻结并回溯:

- 源码版本、配置版本、需求/设计版本、工具链与编译器版本。
- 构建产物 hash、目标板/仿真目标、关键编译选项。
- 单元/集成/系统/HIL 或台架测试报告、覆盖率、静态分析报告。
- 安全相关评审记录、已知问题、风险接受项、release note。

这组材料构成安全案例的最小证据包。CI 的作用不是只给一个"绿灯",而是持续生成、归档并连接这些证据。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| 小 V | 单个特性走的微缩 V:左腿设计逐层对应右腿验证 |
| 左腿 / 右腿 | 左腿=需求/架构/详细设计(分解);右腿=系统-集成/单元测试(验证) |
| DoR / DoD | Definition of Ready / Done——迭代准入 / 准出判据 |
| 可追溯链 | `需求→架构→设计→代码→测试` 的 ID 贯通链 |
| 失效安全 | 故障时回到安全默认态(BMS:接触器 OPEN) |
| 持续合规 | 验证与追溯靠自动化持续满足,而非阶段末人工补 |
| 测试金字塔 | 单元多而快、集成次之、系统/硬件少而精的测试结构 |
| 双轨 | 探索性工作与交付性工作分轨推进 |
| 再基线 | 变更发生时把追溯链与受影响的右腿验证一并同步更新,使完备性证据重新成立 |
| 安全案例 | 围绕安全目标组织的一组可审计论证与证据,用于说明系统在定义边界内足够安全 |
| 证据包 | 支撑某个需求/安全目标的需求、设计、代码、测试、评审、分析与发布基线材料集合 |
| 风险分级验证 | 根据危险程度、失效影响和审核要求决定测试深度、评审强度与是否需要 HIL/台架验证 |
| HIL | Hardware-in-the-loop,用真实或等效硬件闭环验证固件与物理 IO/故障场景的交互 |
